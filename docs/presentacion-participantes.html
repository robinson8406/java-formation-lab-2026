1

Fork = copia del repo central en TU cuenta GitHub

No necesitas ningún permiso en el repo de robinson8406. Haz clic en el botón Fork en GitHub y tienes tu propia copia en segundos. Es gratis.

2

Clone = bajas tu fork a tu máquina

Tu máquina quedará configurada con dos “remotos”: origin apunta a tu fork (donde haces push) y upstream apunta al repo central (donde el formador publica los starts).

3

PR = propones tu entrega al repo central

Cuando terminas, abres un Pull Request desde tu fork hacia el repo central. El CI corre, el reviewer (formador) aprueba y el PR se cierra sin merge. La rama week-XX-start queda intacta para todos.

¿Por qué fork y no trabajar directo en el repo?
Con 200 personas en el mismo repositorio habría conflictos constantes. El fork te da tu propio espacio aislado. Trabajas a tu ritmo sin afectar a nadie.

Flujo completo

Tu recorrido en cada sesión

1

Trae las ramas del formador

El lunes antes de la sesión el formador publica week-XX-start. Tráela desde upstream (repo central), no desde origin.

git fetch upstream
2

Crea tu rama desde el start

Crea tu rama directamente desde la del formador. Nunca trabajes sobre main ni week-XX-start.

git checkout -b week-XX/tu-alias upstream/week-XX-start
3

Implementa, haz tests pasar

Escribe el código, ejecuta los tests localmente. Pipeline verde = listo.

./mvnw test
4

Abre tu PR y asigna formador

Push + PR hacia week-XX-start con el formador como aprobador.

git push origin week-XX/tu-alias
# PR cross-fork: TU-ALIAS:week-XX/alias → robinson8406:week-XX-start
5

PR aprobado → abre tu issue de badge

El badge es un GitHub Issue cerrado con label ✅ completado — no es un certificado, es un registro público en el repo.

Título exacto del issue:
✅ [week-XX] tu-alias completó la sesión

Reglas del PR

Usa el template en .github/PULL_REQUEST_TEMPLATE.md
Asigna exactamente 1 reviewer — formador
El formador valida el checklist de criterios-evaluacion.md
Sin PR aprobado = sesión pendiente (el badge no se otorga)
No bloquea asistencia ni acceso a la siguiente sesión
Convenciones de commit
feat:nueva funcionalidad test:añadir o modificar tests refactor:refactorización sin cambio de comportamiento fix:corrección de bug

¿Qué se espera de cada seniority?

Junior

Implementa y verifica

  • Requerimientos funcionales cumplidos
  • Tests básicos pasando en verde
  • Código que compila y el pipeline no falla
Semi-senior

Diseña y valida

  • Aplica principios SOLID en la solución
  • Tests con casos de borde significativos
  • Separación de responsabilidades visible
Senior

Desacopla y opera

  • Diseño desacoplado y extensible
  • Tests robustos con mocks correctos
  • Criterio no funcional cubierto explícitamente
Experto

Mejora y propone

  • Identifica trade-offs y los documenta
  • Propone mejoras más allá del enunciado
  • El código queda mejor de como lo encontró

La filosofía clave

No hay ejercicios fáciles y difíciles.

Hay una solución mínima que cualquiera puede entregar, y una solución de calidad que demuestra madurez técnica real.

El senior no hace un problema más difícil — hace mejor el mismo problema.
