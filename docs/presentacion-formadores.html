Diseño del reto

Estructura mínima de cada enunciado

1

Cambio funcional

Una historia de usuario concreta, con entrada y salida clara. Debe ser implementable en 20–25 minutos de código.

2

Prueba obligatoria

Al menos 1 test que valide el comportamiento esperado. El andamiaje del test ya viene en el start — el participante lo hace pasar.

3

Criterio no funcional

Elige uno de los cuatro. Garantiza que el reto no sea "solo codear" y diferencia seniorities.

Criterios no funcionales

Calidad — diseño limpio, SOLID, cobertura
Performance — tiempo de respuesta, N+1
Operación — logs, health, métricas
Seguridad — validación input, datos sensibles

Diferenciación por seniority

JuniorReqs funcionales y tests básicos
Semi-seniorSOLID + tests significativos
SeniorDiseño desacoplado, criterio NF cubierto
ExpertoTrade-offs, mejoras, código mejor que lo encontrado

💻 Máquina local del participante
origin → ALIAS/java-formation-lab-2026  (su fork en GitHub)
upstream → robinson8406/java-formation-lab-2026  (repo central — tus starts)
PR cross-fork: fork-ALIAS:week-01/alias → central:week-01-start  ·  se cierra SIN merge
1

Fork = copia del repo central en la cuenta GitHub del participante

No necesita permisos en el repo de robinson8406. Clic en Fork en GitHub y tiene su propia copia en segundos. Es gratis.

2

Clone = baja su fork a su máquina

Se configura con dos remotos: origin apunta a su fork (donde hace push) y upstream apunta al repo central (donde tú publicas los starts).

3

PR = propone su entrega al repo central

Cuando termina, abre un Pull Request desde su fork hacia el repo central. El CI corre, el formador aprueba y el PR se cierra sin merge. La rama week-XX-start queda intacta para todos.

¿Por qué fork y no trabajar directo en el repo?
Con ~200 personas en el mismo repositorio habría conflictos constantes. El fork les da su espacio aislado. Trabajan a su ritmo sin afectar a nadie. Recuérdalo en la sesión 01.

Badges y métricas clave

🏅 ¿Qué es un badge?

Un badge no es un certificado ni un archivo — es un GitHub Issue cerrado con el label ✅ completado.

Sirve como registro público en el repo: filtras issues por ese label y ves exactamente quién completó qué sesión.
● ✅ [week-02] robinson completó la sesión
✅ completado week-02 abierto por robinson8406 · cerrado por formador

📋 Flujo paso a paso

  1. 1
    Participante abre PR desde week-XX/tu-alias hacia week-XX-start en el repo central
  2. 2
    Pipeline CI se activa automáticamente — debe quedar verde ✅ antes de continuar
  3. 3
    Formador revisa la implementación, da feedback y aprueba el PR validando criterios-evaluacion.md
  4. 4
    Participante abre un Issue con título exacto: ✅ [week-XX] alias completó la sesión
  5. 5
    Formador verifica el PR aprobado, cierra el issue y aplica label completado → badge otorgado
