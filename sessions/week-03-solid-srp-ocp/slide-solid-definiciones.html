S · SRP

Single Responsibility Principle

Una clase debe tener una única razón para cambiar. Si mezcla orquestación + reglas de negocio, un cambio en una rompe la otra.

⚠️ Síntoma: tests de stock fallan al tocar código de descuentos.
OrderProcessor
├─ StockValidator   // 1 razón: stock
├─ OrderNotifier    // 1 razón: notificar
└─ DiscountCalculator // 1 razón: descuentos
O · OCP

Open/Closed Principle

El código debe estar abierto a extensión, cerrado a modificación. Agregar un caso nuevo no debe tocar los casos existentes.

⚠️ Síntoma: cada descuento nuevo obliga a editar el mismo if/else.
// agregar LOYALTY:
+ case LOYALTY -> ...
// STANDARD y SEASONAL: 0 líneas tocadas
Hoy refactorizamos OrderProcessor: separamos responsabilidades (SRP) y agregamos un descuento nuevo sin tocar el código existente (OCP).
⚠️ Antes — todo en 1 clase
classDiagram
    class OrderProcessor {
      +process(order, stock)
      valida stock
      if STANDARD desc 5%
      if SEASONAL desc 20%
      notifica cliente
    }
3 razones para cambiar · agregar LOYALTY = editar esta clase (rompe SRP y OCP)
✅ Después — SRP + OCP aplicados
classDiagram
    class OrderProcessor {
      +process(order, stock)
    }
    class StockValidator {
      +hasEnoughStock(available, requested)
    }
    class OrderNotifier {
      +notifyCustomer(email, msg)
    }
    class DiscountCalculator {
      +apply(price, type)
    }
    class DiscountType {
      <<enumeration>>
      STANDARD
      SEASONAL
      LOYALTY
    }
    OrderProcessor --> StockValidator
    OrderProcessor --> OrderNotifier
    OrderProcessor --> DiscountCalculator
    DiscountCalculator --> DiscountType
4 clases, 1 razón cada una · LOYALTY se agrega sin tocar STANDARD/SEASONAL
