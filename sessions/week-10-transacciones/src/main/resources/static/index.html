Transacciones en Spring Boot

Una transferencia no puede quedarse a medias. Las transacciones permiten tratar varias operaciones como una sola unidad de trabajo.

01 / Transacción 02 / ACID 03 / @Transactional 04 / Propagación 05 / Rollback 06 / Solo lectura
01

Todo o nada

Una transacción agrupa operaciones sobre la base de datos. Si todas terminan correctamente, se confirman con un commit. Si se decide cancelar, un rollback revierte los cambios de esa transacción.

Por ejemplo: transferir $100 de la cuenta A a la cuenta B exige descontar en una y sumar en la otra. Ambas modificaciones deben confirmarse juntas.

El alcance importa: una transacción de base de datos no deshace automáticamente un correo enviado ni una llamada a una API externa.

02

Las cuatro garantías: ACID

A Atomicidad

Se aplican todas las operaciones o ninguna. No puede quedar confirmado solo el débito de la transferencia.

C Consistencia

La base pasa de un estado válido a otro, respetando restricciones y reglas correctamente implementadas. En el ejemplo, el total sigue siendo $700.

I Aislamiento

Controla cómo se afectan las transacciones concurrentes. Las garantías concretas dependen del nivel de aislamiento; no significa que todas se ejecuten en serie.

D Durabilidad

Después del commit, los cambios deben persistir incluso ante un reinicio o fallo, según las garantías del motor y su configuración.

03

@Transactional

La anotación de Spring org.springframework.transaction.annotation.Transactional declara el límite transaccional de un método o una clase. Spring usa un gestor de transacciones para abrir o reutilizar una transacción y decidir su commit o rollback al terminar la llamada.

@Service
public class TransferenciaService {
    @Transactional
    public void transferir(Long origen, Long destino, BigDecimal monto) {
        debitar(origen, monto);
        acreditar(destino, monto);
    }
}

Configuración predeterminada de las opciones relevantes:

OpciónValor por defectoPara qué sirve
propagationREQUIREDDecide si se reutiliza una transacción existente o se crea una nueva.
isolationDEFAULTUsa el aislamiento predeterminado del motor de base de datos.
timeout-1Sin tiempo límite explícito en la anotación: se usa el del gestor, si lo tiene. Un valor positivo se expresa en segundos.
readOnlyfalsePermite declarar que la unidad de trabajo solo consulta datos para facilitar optimizaciones.
rollbackFor{} (sin reglas adicionales)Añade tipos de excepción que deben provocar rollback. Por defecto, Spring lo hace ante RuntimeException y Error, no ante excepciones checked.

Ojo con el proxy: en el modo habitual de Spring, la llamada debe entrar desde otro bean al método transaccional. Una llamada interna como this.otroMetodo() no activa una nueva configuración de @Transactional. Coloca el límite de negocio en un servicio.

Las reglas de rollback descritas son las estándar, sin una política global personalizada. En Spring reciente pueden cambiarse globalmente.

04

Compartir o independizar

La opción habitual

Propagation.REQUIRED

Si ya hay una transacción, el método participa en ella. Si no la hay, crea una. Es el valor predeterminado.

Servicio A [TX1]
→ Servicio B [misma TX1]

Úsalo cuando: todas las operaciones forman una sola unidad de negocio, como debitar y acreditar una transferencia.

Si un método participante marca la transacción como rollback-only, el conjunto no podrá confirmarse aunque el método exterior capture la excepción; puede recibir UnexpectedRollbackException al intentar confirmar.

Una unidad independiente

Propagation.REQUIRES_NEW

Suspende la transacción actual, si existe, y crea otra independiente. Si no hay una previa, también crea una nueva.

Servicio A [TX1 pausada]
→ Servicio B [TX2] → reanuda TX1

Úsalo cuando: un registro de auditoría debe persistir aunque la operación principal termine en rollback.

Si TX2 confirma, un rollback posterior de TX1 no la revierte. Si TX2 falla y su excepción se propaga, también puede provocar rollback en TX1 según sus reglas.

@Service
public class AuditoriaService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void registrarIntento(String detalle) {
        auditoriaRepository.save(new Auditoria(detalle));
    }
}

El servicio principal inyecta AuditoriaService y llama a registrarIntento(...) a través del bean de Spring. El fragmento presupone el repositorio y su inyección.

Coste de REQUIRES_NEW: con JPA/JDBC suele necesitar otra conexión mientras la exterior retiene la suya. Dimensiona el pool y evita que la auditoría dependa de filas aún no confirmadas o bloqueadas por la transacción exterior.

05

Rollback también para checked

Una excepción checked, como IOException o una excepción de negocio que extiende Exception, no provoca rollback por defecto. Usa rollbackFor si ese fallo debe cancelar toda la operación.

@Transactional(rollbackFor = SaldoInsuficienteException.class)
public void transferir(Long origen, Long destino, BigDecimal monto)
        throws SaldoInsuficienteException {
    debitar(origen, monto);
    acreditar(destino, monto);
}

En este ejemplo, SaldoInsuficienteException es checked. La regla incluye ese tipo y sus subclases; las reglas estándar para RuntimeException y Error se mantienen.

La excepción debe salir del método interceptado para que Spring aplique la regla. Si la capturas y la ocultas dentro del método, rollbackFor por sí solo no fuerza la reversión. Prefiere excepciones específicas; usa rollbackFor = Exception.class solo si cualquier excepción debe cancelar la operación.

06

¿Cuándo usar readOnly?

Usa @Transactional(readOnly = true) en servicios que solo leen: búsquedas, listados y reportes sin modificaciones. La transacción sigue existiendo, pero comunica una intención de solo lectura al gestor y al proveedor JPA.

@Transactional(readOnly = true)
public List<CuentaDto> consultarCuentas() {
    return cuentaRepository.findAll().stream()
            .map(CuentaDto::from)
            .toList();
}
  • Puede optimizar: con Hibernate y la integración de Spring puede reducir trabajo de seguimiento de cambios y ajustar el comportamiento de flush. El efecto depende del proveedor y de la configuración.
  • No es seguridad: no garantiza bloquear escrituras en todos los motores. No lo uses como sustituto de permisos ni para métodos que llaman a save, delete o modifican entidades.
  • No redefine una transacción existente: con REQUIRED, si el método se une a una transacción de escritura, prevalecen las características de la transacción exterior.

Una operación de negocio, un límite claro. REQUIRED para trabajar juntos; REQUIRES_NEW solo cuando la independencia sea intencional.
